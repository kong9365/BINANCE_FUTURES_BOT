# 전략 현실성 분석 & 개선 계획 — Binance USDT-M 선물 봇

> 작성: 2026-05-21 | 분석 데이터: 캐시 12종목 × 501 bar(1h) = 6,012 bar(~20일) | 실거래 GO: **HOLD 유지**

## Context (왜 이 문서가 존재하는가)
실거래 투입 전 안정화 과정에서, 현 매수 전략(OI-급증 모멘텀)이 (a) 현 임계로 사실상 무거래,
(b) 거래해도 끝난 스파이크를 추종(역선택)한다는 의심이 제기됐다. 본 문서는 이를 **실데이터로
정량 검정**하고, 그 결과에 따라 **검증 가능한 엣지를 가진 전략으로 교체**하는 단계별 계획을
제시한다. 또한 운영자 요청으로 모든 영속 데이터를 **Supabase(주저장) + 로컬 sqlite(안전망)**로
이관한다. 각 단계는 **검증 게이트**를 통과해야 다음으로 넘어가며, 회귀를 방지한다.

## 1. 정량 진단 결과 (현 OI-급증 전략)

### 1-A. 재보정 그리드 — 64개 전 조합이 손실
(룩백 L × OI임계 × 가격임계) 격자 전수 백테스트(TP+2%/SL−1%, 최대보유 24h, 왕복비용 0.26% 반영):

| 구성 | 거래 | 승률 | 기대값/트레이드 | PF |
|---|---|---|---|---|
| **최선** L=1, OI≥1.5%, P≥0.7% | 26 | 38.5% | **−0.064%** | 0.91 |
| L=3, OI≥1.0%, P≥0.7% | 93 | 35.5% | −0.241% | 0.69 |
| L=6, OI≥1.0%, P≥0.5% | 129 | 32.6% | −0.276% | 0.65 |
| 대부분의 조합 | — | 15~35% | −0.3 ~ −0.9% | 0.2~0.7 |

→ **"가장 덜 나쁜" 조합조차 PF 0.91로 손실.** 임계 재보정으로는 흑자 전환 불가.

### 1-B. 역선택 검정 — 엣지의 *부호*를 직접 측정 (핵심)
신호 발생 후 *신호 방향*으로의 평균 forward return:

| 보유 | OI≥1.5%/P≥0.7% (신호 38건) | OI≥1.0%/P≥0.5% (신호 80건) |
|---|---|---|
| +1 bar | +0.176% (양 63%) | −0.044% (양 51%) |
| +3 bar | +0.151% (양 55%) | −0.072% (양 49%) |
| +6 bar | **−0.029% (양 47%)** | **−0.270% (양 46%)** |
| +12 bar | +0.100% (양 55%) | −0.213% (양 46%) |

→ 진짜 모멘텀은 **1~3시간만 약하게(+0.15%)** 살아있다가 **6시간 내 소멸·반전**. 그 +0.15%가
**왕복 비용 0.26%보다 작다.** 신호를 느슨하게 풀면(거래↑) **전 구간 음수**(순수 평균회귀).

### 1-C. 결론
- 현 전략은 **재보정 대상이 아니라 교체 대상**. 20일 표본의 모든 파라미터에서 음의 기대값.
- 미세한 단기 모멘텀 < 비용. **TP2/SL1 구조의 1% 손절이 알트 노이즈 안**이라 승률 15~38%로 깔림.
- ⚠️ 한계: 20일·단일 레짐·26~130거래 → **방향성은 강하나 통계적 확정은 아님**. 그래서 교체 후
  **다년 walk-forward 검증(거래≥200)**이 필수(P4).

## 2. 전략 리서치 & 채택

7개 전략군(펀딩 캐리/극단, OI+CVD, 돌파, 추세추종, 평균회귀, 횡단면 모멘텀, 스탯아브)을 조사.
제약(스팟 레그 금지=보호자산 룰, 틱/L2 데이터 없음, 비용 0.26% → 0.5%+ 움직임 필요, 보수적·백테스트
가능·~일단위 빈도)에 비추어 **레짐 전환형 단일 봇**을 채택.

| 모드 | 전략 | 엣지 가설 | 프로파일 |
|---|---|---|---|
| **추세장(ADX>25)** | **Donchian/ATR 돌파** | 암호화폐의 강한 추세 지속성 — N기간 고점 돌파 = 새 추세, 두꺼운 우측꼬리 포착 | 저승률(35~45%)·고R(2.5~4:1) |
| **횡보장(ADX<20)** | **펀딩 극단 역추세 페이드 (OI 확인)** | 극단 펀딩 = 한쪽 쏠림(군중). 한계수요 소진 시 프리미엄 붕괴·청산 → **소진된 쪽을 페이드**. 현 전략 역선택의 거울상 | 고승률(45~60%)·R 1.5~2.5:1 |

**채택 근거**: 둘 다 보유 데이터(OHLCV+펀딩+OI)로 백테스트 가능, 스팟 레그 불필요(보호자산 룰 무충돌),
~일단위·보수적, 목표 움직임 ≥0.5~1.5%로 비용 상회, 추세 vs 회귀라 **음의 상관**으로 자본곡선 평탄화.
**v2 보류**: 횡단면 모멘텀(바스켓 실행·유니버스 관리 복잡). **제외**: 캐리/스탯아브(스팟·MM 인프라 필요).

**구현 순서(운영자 결정)**: ① **돌파 먼저**(OHLCV만, 가장 단순·견고·즉시 백테스트) → ② 펀딩 페이드 나중.

> 출처: ScienceDirect 2025(펀딩 아브 위험/수익), CryptoCred(OI/CVD), Turtle/Donchian(추세),
> Han·Kang·Ryu SSRN 4675565(암호 모멘텀 Sharpe≈1.5), Stoic Research(ORB Sharpe≈1) 등.
> 상세 리서치는 본 세션 리서치 산출물 참조.

## 3. 데이터 영속화 (Supabase 주저장 + 로컬 안전망)

운영자 요청: 모든 DB(거래·체결·시그널·자본·로그)를 Supabase에 저장.
**채택 방식**: Supabase(Postgres 17, 프로젝트 `aoeqgptytzuhvvchsgul` "Binance") **주저장** +
로컬 sqlite **폴백 큐**(네트워크 장애 시 거래 중단 방지, 재연결 시 동기화). 트레이딩 루프 안정성 보장.

**런타임 접근**: 봇은 `supabase-py`(또는 psycopg)로 접속(env: `SUPABASE_URL`/`SUPABASE_KEY`,
시크릿은 .env·미커밋). 스키마 마이그레이션·검증 쿼리는 Claude의 Supabase MCP로 관리.

**스키마(초안, public)**:
| 테이블 | 용도 |
|---|---|
| `trades` | 거래 생애주기(진입·청산·PnL·R·수수료·레짐·전략·사유) |
| `signals` | 신호/게이트 통과 여부 + 피처(jsonb) |
| `position_events` | 포지션 상태 변화 이벤트 |
| `equity_snapshots` | 자본 스냅샷(wallet/available/margin/unrealized) |
| `oi_history` / `funding_history` | OI·펀딩 롤링 누적(바이낸스 30일 한계 극복) |
| `ohlcv` | 캔들 누적(taker_buy_base 포함 — CVD 프록시용) |
| `regime_log` | 레짐 분류 이력(ADX/EMA/ATR) |
| `events` | 앱 로그·에러(레벨·컴포넌트·메시지) |
| `backtest_runs` | 백테스트 실행 결과(파라미터 jsonb·지표) — 회귀 기준선 |

시간은 모두 `timestamptz`(UTC), 유연 필드는 `jsonb`.

## 4. 단계별 개선 계획 (각 단계 = 검증 게이트 통과 필수)

> 공통 회귀 방지: 매 단계 ⓐ `pytest tests/` 전체 그린, ⓐ 신규 모듈 `tests/test_*.py` 동반,
> ⓒ 백테스트 룩어헤드 가드(close 확정 후 신호, `shift(-1)` 금지), ⓓ 기준 지표를 `backtest_runs`에
> 기록해 재실행 시 회귀 감지, ⓔ "A안" GitHub 반영(보안스캔→테스트→명시 add→커밋→push).

### P0 — Supabase 영속 계층 (주저장 + 로컬 폴백)
- Supabase 스키마 적용(MCP migration). 봇 `data/persistence.py` 어댑터: Supabase 쓰기 + 실패 시
  로컬 sqlite 큐 적재 → 재연결 시 flush. 기존 sqlite 스키마와 호환 매핑.
- **검증**: mock 라운드트립 단위테스트, 네트워크 장애 폴백·재동기 테스트, `list_tables`로 스키마 확인,
  실제 1행 write→read 통합 점검(read-only 데이터).

### P1 — 레짐 엔진 + Donchian/ATR 돌파 전략 (백테스트)
- `strategy/breakout.py`(또는 기존 strategy 확장): ADX(14)+200EMA 레짐, Donchian(20/55) 돌파,
  ATR(14) 기반 초기 스톱(~2 ATR)·사이징, 청산=반대 채널(10기간)/ATR 트레일.
- `backtesting/backtest_engine.py`에 `strategy="breakout"` 추가(룩어헤드 차단).
- **검증**: 지표 정확성 단위테스트(알려진 값), 룩어헤드 테스트, 캐시+누적 데이터 백테스트로
  기대값·PF·MDD 측정 후 `backtest_runs` 기록. (저승률·고R 특성 확인.)

### P2 — 라이브 통합 (HOLD 유지)
- 돌파 신호를 라이브 결정 경로에 통합(RiskManager/CostGuard/PairWhitelist/보호종목/preflight **그대로**).
- **검증**: 통합 테스트, testnet dry-run(exit 0·ERROR 0), preflight·예산 cap 동작. **실거래 GO=HOLD.**

### P3 — 펀딩 극단 페이드 (횡보 모드)
- 펀딩/OI 누적 선행 → percentile 극단 + OI 롤오버 확인 역추세 페이드(ADX<20 게이트).
- **검증**: 백테스트(횡보 구간), 단위테스트, knife-catch 방지(확인 트리거) 검증.

### P4 — 데이터 누적 + walk-forward 튜닝
- OHLCV/펀딩/OI 누적 확장(P0 테이블에 적재) → 수개월 후 walk-forward(거래≥200, OOS Sharpe≥1.0,
  PF≥1.2, MDD<20%) 검증·튜닝. 통과 못하면 전략 재검토/폐기.
- **검증**: walk-forward 지표, OOS 성능, 기준선 대비 회귀 체크.
